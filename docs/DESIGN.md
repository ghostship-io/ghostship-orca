# Design

This document records the facts the implementation depends on, how they were
established, and the decisions that follow from them. Every claim about
OrcaSlicer behaviour cites the source that proves it.

## The problem

OrcaSlicer's built-in flow calibration is a modifier sweep driven from the
*Calibration* menu. It works, but:

- the range and step are fixed by the pass you pick;
- the objects are generated by Orca internals and cannot be inspected or reused;
- there is no automated way to run the Ellis print-and-inspect workflow.

The goal here is a local generator that produces the Ellis plate once, labels
it, and loads it into the running slicer.

## How OrcaSlicer loads a 3MF

There are two importers, and the choice is made by the file's content.

`Model.cpp:509-528`:

1. `PrusaFileParser::check_3mf_from_prusa()` scans `3D/3dmodel.model`.
2. If the `<metadata name="Application">` value contains `PrusaSlicer`, the file
   goes to `load_3mf()` (the Prusa reader).
3. Otherwise it goes to `load_bbs_3mf()` (the Bambu/Orca reader).

`check_3mf_from_prusa` only inspects the Application tag, and it is skipped
entirely when `3D/_rels/3dmodel.model.rels` exists (`3mf.cpp:319-340`) — but the
tag is still the decisive input, so we do three things:

- declare `Application` as `OrcaSlicer-<version>` (the Orca prefix is recognised
  by `_handle_end_metadata`, `bbs_3mf.cpp:4074-4090`);
- declare a separate `<metadata name="OrcaSlicer">` tag, which Orca treats as
  authoritative for version detection;
- omit `3D/_rels/3dmodel.model.rels` entirely.

**Consequence:** object-level settings are only parsed by the Bambu/Orca
reader. `_3MF_Importer` (Prusa) never reads `Metadata/model_settings.config`
at all — its name for that concept is `Metadata/Slic3r_PE_model.config`. Writing
a Prusa-shaped file would silently drop every flow-ratio override.

## Where per-object settings live

`bbs_3mf.cpp:228` defines `BBS_MODEL_CONFIG_FILE = "Metadata/model_settings.config"`.

The object block is written by `_add_model_config_file_to_archive`
(`bbs_3mf.cpp:8050+`) and read by `_handle_start_config_object` /
`_handle_start_config_metadata`. Object config keys are applied through
`model_object->config.set_deserialize(key, value, ...)` (`bbs_3mf.cpp:2236`),
so any option present in the object's config definition can be set per object.

`print_flow_ratio` is defined in `PrintConfigDef::init_fff_params`
(`PrintConfig.cpp:2755`) and lives in `StaticPrintConfig`, which is part of
`PrintObjectConfig` (`PrintConfig.hpp:2018`). `ModelObject::config` is the
object-scope config store, so the override applies.

### Identity constraints

- Object `id` attributes in `model_settings.config` must match the resource
  object ids in `3dmodel.model`. The reader rejects duplicates
  (`_handle_start_config_object`, `bbs_3mf.cpp:4396-4406`).
- A `<part>` must carry the mesh resource id, because the loader matches
  volumes by `subobject_id` (`_generate_volumes_new`, `bbs_3mf.cpp:5094+`).
- Build item transforms are **4x3 column-major** (`r` varies fastest), per
  `bbs_get_transform_from_3mf_specs_string` (`bbs_3mf.cpp:621`). The exporter
  writes them the same way in `add_transformation`.

## The flow-ratio math

Orca applies the flow factors multiplicatively. `GCode.cpp:8233-8236`:

```cpp
double filament_flow_ratio = FILAMENT_CONFIG(filament_flow_ratio);
auto _mm3_per_mm = path.mm3_per_mm * this->config().print_flow_ratio;
_mm3_per_mm *= filament_flow_ratio;
```

So:

```
effective_extrusion = geometric_volume × print_flow_ratio × filament_flow_ratio
```

Orca's own calibration writes `print_flow_ratio = 1 + modifier/100`
(`CalibUtils.cpp:813`), i.e. a multiplier relative to the filament.

### Decision

The user's requirement is that each cube be labelled with its *actual* flow
ratio and that a separate filament profile not be required. Those together
force:

```
object_override = target_multiplier / filament_flow_ratio
```

- The label is the absolute, effective extrusion multiplier.
- The filament profile is untouched.
- The override stays in the same coordinate space Orca expects (a multiplier).

Alternatives considered and rejected:

- **Raw override = target.** Simplest, but then the label is only true when the
  filament ratio is exactly 1.0. The user would have to edit their filament
  profile back to 1.0 to get correct results, and then edit it back again —
  exactly the manual step this tool exists to remove.
- **Relative modifier (Orca YOLO style).** Reproduces Orca's existing feature,
  which is the thing being improved on.

A unit test asserts `stored_override × filament_ratio == label` for the whole
plate, so this invariant cannot silently regress.

## Ellis print settings

From Ellis' guide (`docs/ELLIS_METHOD.md`), the generated plate sets:

| Setting | Value | Why |
| --- | --- | --- |
| `top_surface_pattern` | `monotonic` | Uniform top surface, easiest to judge |
| `top_shell_layers` | 6 | Compounds the multiplier difference |
| `bottom_shell_layers` | 2 | Leaves infill so first-layer squish does not reach the top |
| `sparse_infill_density` | 35% | Enough support under the top skin |
| `sparse_infill_pattern` | `rectilinear` | Predictable support |
| `ironing_type` | `no ironing` | Ironing hides the surface we are judging |
| `wall_loops` | 2 | Standard test-cube walls |

These go in `Metadata/project_settings.config` as sparse JSON. Orca merges
`project_settings.config` into the active config
(`_extract_project_config_from_archive` → `DynamicPrintConfig::load_from_json`),
so unspecified keys keep the user's current process settings.

## Handoff

OrcaSlicer is single-instance; the mechanism differs per platform
(`InstanceCheck.cpp`):

- **Windows** — the running instance advertises its identity as window
  properties `Instance_Hash_Minor` / `Instance_Hash_Major`. A second launch
  finds the window, then sends the command line as a `WM_COPYDATA`
  (`dwData = 1`) message (`InstanceCheck.cpp:104-164`).
- **macOS** — `send_message_mac` delivers an Apple event registered by
  instance hash (`InstanceCheck.cpp:216-232`).
- **Linux** — the second process takes a lock file in `<data_dir>/cache`, then
  sends a DBus `AnotherInstance` method call on the **session** bus to
  `com.orcaslicer.OrcaSlicer.InstanceCheck.Object<hash>`
  (`InstanceCheck.cpp:240-300`, listener at `540-690`).

All three are triggered by *launching the executable with the file path as a
positional argument* (`process_command_line`, `InstanceCheck.cpp:79-100`).

### Decision

We launch the executable. We do **not** attempt the DBus call ourselves:

- the object name embeds `get_instance_hash_string()`, which is a hash of the
  canonical executable path (or `$APPIMAGE`) computed internally by Orca and
  never published;
- reproducing that hash would break on any path change and is far more brittle
  than launching the binary.

On macOS, `open -a` is used because that is the mechanism Orca registers for.

## Why not in-slicer object creation

OrcaSlicer's Python plugin API (`src/slic3r/plugin/`) is **read-only over the
model**. `PluginHostModel.cpp` binds `Model`, `ModelObject`, `ModelVolume` with
`py::nodelete` non-owning references and exposes only getters — there is no
`add_object` and no way to place geometry on the bed. A plugin can read the
scene, transform slices in the slicing pipeline, and write the exported
G-code, but it cannot construct a plate.

Therefore the plugin's job is to *generate a file and load it*, which is what
the handoff does. This is also why the CLI exists as a first-class surface: it
performs the same work without depending on the plugin API at all.

## Trade-offs

- **One box mesh repeated per object.** Each cube is a separate 3MF object with
  its own config, so overrides are per-object as required. The plate is a few
  kilobytes larger than a shared-mesh file would be; that is irrelevant at this
  scale and avoids the shared-mesh metadata the reader also supports but which
  adds complexity.
- **No thumbnails.** Orca generates them on load. Adding them would mean
  shipping a renderer for no functional gain.
- **`project_settings.config` is sparse.** This is deliberate: it embeds only
  the calibration-specific overrides, preserving the user's active process.
